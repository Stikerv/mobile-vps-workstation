# Mobile VPS Workstation — Полная архитектура

**Версия:** 1.0
**Статус:** Проектирование
**Основная платформа:** Ubuntu VPS
**Мобильный клиент:** Android + Termux
**Репозиторий:** `Stikerv/mobile-vps-workstation`

---

## 1. Назначение проекта

Mobile VPS Workstation — персональная мобильная рабочая станция разработчика, построенная на удалённом Ubuntu VPS и управляемая со смартфона.

Цель — получить полноценную серверную среду для:

- разработки Python-приложений и API;
- создания SaaS-продуктов;
- работы с Git и GitHub;
- запуска Telegram-ботов;
- работы с Docker и базами данных;
- развёртывания автоматизаций;
- интеграции AI-инструментов;
- управления собственными сервисами.

Основной принцип: смартфон выступает интерфейсом управления, VPS — вычислительной и серверной платформой, GitHub — системой контроля версий и хранения инфраструктурного кода.

## 2. Общая архитектура

Система состоит из пяти логических уровней.

### Уровень A. Mobile Client

Устройство: Android.

Основной инструмент: Termux.

Компоненты:

- OpenSSH Client — удалённое подключение;
- Git — управление репозиториями;
- Python — локальные утилиты;
- SSH Config — профили подключений;
- Termux:API — дополнительные возможности Android при необходимости.

Функции:

- подключение к VPS;
- запуск команд;
- управление Git;
- просмотр логов;
- администрирование сервисов;
- выполнение резервных и диагностических операций.

### Уровень B. Secure Access Layer

Отвечает за безопасное подключение к серверу.

Компоненты:

- SSH Server;
- SSH-ключи Ed25519;
- отдельный административный пользователь;
- ограничение привилегий через sudo;
- настройка SSH;
- firewall;
- резервный доступ через консоль провайдера.

Принципы:

- запрет входа по паролю после проверки ключевого доступа;
- запрет прямого SSH-входа под root;
- минимально необходимые права;
- отсутствие приватных ключей в GitHub;
- сохранение рабочего способа восстановления доступа.

### Уровень C. Ubuntu Server Core

Базовая операционная система и инфраструктура.

Основные компоненты:

- Ubuntu LTS;
- systemd;
- OpenSSH;
- UFW или другой выбранный firewall;
- unattended-upgrades;
- Git;
- Python 3;
- pip/venv;
- curl;
- wget;
- rsync;
- htop;
- tmux.

Функции:

- управление пользователями;
- установка пакетов;
- управление процессами;
- контроль системных служб;
- обновление ОС;
- сбор системной информации.
### Уровень D. Development Environment

Среда разработки и выполнения приложений.

Компоненты:

- Python virtual environments;
- Docker Engine;
- Docker Compose;
- Git;
- Nginx;
- PostgreSQL;
- Redis — при необходимости;
- инструменты тестирования и линтинга.

Не все компоненты устанавливаются сразу. Каждый модуль подключается по мере появления реальной потребности.

Предусматриваются отдельные рабочие пространства для проектов:

`/opt/projects/`

Например:

- `/opt/projects/telegram-flow-saas`
- `/opt/projects/hidden-habitat-tools`
- `/opt/projects/other-services`

Системные конфигурации располагаются отдельно от пользовательского кода.

### Уровень E. Application & AI Layer

Прикладной уровень для запуска собственных продуктов.

Возможные направления:

- FastAPI;
- Telegram Bot API;
- SaaS-приложения;
- фоновые задачи;
- webhook-сервисы;
- AI API-интеграции;
- автоматизация бизнес-процессов.

Каждый продукт должен иметь независимую конфигурацию, зависимости, логи и способ запуска.

## 5. Модель безопасности

### Аутентификация

- SSH-ключи Ed25519;
- отдельный пользователь;
- root login отключается после проверки альтернативного доступа;
- пароли и токены не попадают в Git.

### Сетевая защита

- firewall с политикой запрета входящих соединений по умолчанию;
- открытие только необходимых портов;
- ограничение доступа к административным интерфейсам;
- проверка конфигурации перед применением.

### Управление секретами

Секреты хранятся на сервере в защищённых файлах или в подходящем менеджере секретов.

Примеры:

- Telegram Bot Token;
- API keys;
- пароли баз данных;
- приватные SSH-ключи;
- ключи внешних сервисов.

В репозитории разрешено хранить только примеры конфигурации без действительных секретов.

### Принцип изменений

Каждый установочный скрипт должен:

1. Проверять операционную систему.
2. Проверять необходимые права.
3. Показывать план изменений.
4. Проверять текущую конфигурацию.
5. Выполнять только необходимые действия.
6. Возвращать понятный результат.

## 6. Управление сервисами

Для системных служб используется systemd.

Для контейнеризированных приложений — Docker Compose.

Каждый сервис должен иметь:

- конфигурацию;
- способ запуска;
- способ остановки;
- проверку состояния;
- журналы;
- инструкцию восстановления.

Управление осуществляется через SSH.

Примеры команд:

```bash
systemctl status nginx
docker compose ps
docker compose logs -f
journalctl -u nginx -n 100
---

## 8. Мониторинг и диагностика

Базовые показатели:

- загрузка CPU;
- использование RAM;
- свободное дисковое пространство;
- состояние служб;
- доступность SSH;
- состояние Docker-контейнеров;
- ошибки в журналах.

Первый этап использует системные инструменты Linux.

Позже при необходимости добавляются:

- Prometheus;
- Grafana;
- exporters;
- уведомления в Telegram.

## 10. Критерии готовности

Первая версия считается рабочей, если:

1. VPS доступен через SSH с Android.
2. Доступ настроен с использованием SSH-ключа.
3. Root-вход по SSH отключён после проверки безопасного доступа.
4. Firewall работает и пропускает только необходимые соединения.
5. Git работает на сервере.
6. Python и виртуальные окружения работают.
7. Docker запускает тестовый контейнер.
8. Есть базовая диагностика системы.
9. Есть проверенная процедура резервного копирования.
10. Сервер можно восстановить по документации.

## 11. Архитектурные принципы

1. Безопасность важнее удобства.
2. Простая система предпочтительнее преждевременной сложности.
3. Каждый компонент должен иметь определённую ответственность.
4. Установка должна быть воспроизводимой.
5. Скрипты должны быть идемпотентными, где это возможно.
6. Конфигурация должна быть отделена от кода.
7. Секреты никогда не хранятся в Git.
8. Изменения инфраструктуры должны быть проверяемыми.
9. Новые технологии подключаются только при наличии практической задачи.
10. Управление должно оставаться доступным с мобильного устройства.

**Итог:** Mobile VPS Workstation — модульная персональная инфраструктура разработки, позволяющая использовать Android как мобильный интерфейс управления полноценным Linux-сервером и постепенно превращать его в платформу для собственных IT-продуктов.
